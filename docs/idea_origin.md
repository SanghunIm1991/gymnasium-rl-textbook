# Gymnasiumのサンプル環境で強化学習を順番に学ぶ教科書づくり

> この文書は、教科書の企画の段階の元の記録です。実際に決まった方針は [CLAUDE.md](../CLAUDE.md) と [QA表](qa_log.md) にあります。

## 概要・きっかけ

Python の強化学習ライブラリ [Gymnasium](https://gymnasium.farama.org/)（Farama Foundation がメンテナンスしている、OpenAI Gym の後継）には、難易度の異なる標準のサンプル環境がそろっている。これらを**易しい環境から順に1つずつ解いていく構成の教科書（学習資料）**を自作する。アルゴリズムの説明と実装、学習結果の観察をセットにして、章が進むごとに手法と環境の両方が一段ずつ難しくなるように組み立てる。

「教科書」はアプリではなく、学習教材をつくる企画。自分の学習記録を兼ねつつ、後から読み返して再現できる形にまとめることを狙う。

**位置づけ**: 深層強化学習を一部で扱う著者の別の企画とは、**独立したコンテンツ**とする。内容が一部重なっても、互いを前提にせず、この教科書だけで完結させる。

**読む環境**: ブラウザで GitHub のリポジトリを開いて、そのまま読めることを必須とする。GPU のある環境・ない環境のどちらでも、同じ教材で実行できるようにする。

## 評価

- **良い点**
  - Gymnasium の環境は API（`reset()`／`step()`）が共通なので、同じ学習ループの骨組みのまま環境とアルゴリズムだけを差し替えて章を積み上げられる
  - 表形式（Toy Text）→ 連続状態（Classic Control）→ 連続行動・物理シミュレーション（Box2D／MuJoCo）という難易度の階段が、標準の環境だけで自然にできる
  - Classic Control の環境は軽く、GPU が無く CPU だけでも数分〜数十分で学習を回せる
- **懸念点**
  - 公式サイトのチュートリアルや既存の書籍・記事と内容が重なりやすい。単なる写しで終わらせない工夫（自分で実装し直す、比較実験を入れる等）が要る
  - Box2D 系の環境は依存パッケージ（`box2d-py`）のビルドに SWIG 等が必要になることがあり、Windows では導入でつまずきやすい（着手時に公式の導入手順で確認する）
  - MuJoCo 系（Hopper／Humanoid 等）は学習に時間がかかり、CPU だけでは章の実験を回しきれない可能性がある
  - Atari 系は追加パッケージ（`ale-py`）とゲームROMの扱いが絡むため、権利面を含めて対象にするかを検討する必要がある

## 肉付け（教科書の構成案）

教科書は、次の順に読む3つの部分と、それらから参照するクラス図で構成する。

1. **概要資料**（演習の前に読む）
2. **Windows での環境構築マニュアル**
3. **演習**（Gymnasium の環境を順に解く。下の章立て表）
4. **クラス図**（必要になった時点で、その都度追加する）

### 1. 概要資料

演習に入る前に、使う道具と理論の全体像をつかむための資料。各資料に入れる内容（案。着手時に見直す）:

| 資料 | 主な内容 |
|---|---|
| 強化学習の概要 | エージェントと環境、状態・行動・報酬、収益と割引、価値関数と方策、探索と活用、モデルフリー／モデルベース、方策オン／オフ、手法の地図（表形式 → DQN → 方策勾配 → Actor-Critic → PPO／SAC）と、演習のどの章で扱うかの対応 |
| Gymnasium の概要 | OpenAI Gym からの経緯、`gymnasium.make()` と環境の一覧、`reset()`／`step()` の戻り値（`terminated` と `truncated` の違いを含む）、`observation_space`／`action_space`（`Discrete`・`Box` 等）、ラッパー、`render_mode`、ベクトル化環境 |
| Stable-Baselines3 の概要 | 収録アルゴリズムと、それぞれが対応する行動空間（離散／連続）の一覧、方策（`MlpPolicy` 等）、`learn()`／`predict()`／`save()`／`load()`、コールバック、ベクトル化環境（`VecEnv`）、評価（`evaluate_policy`）、`device` の指定 |
| PyTorch の概要 | テンソル、自動微分（autograd）、`nn.Module` によるネットワークの定義、損失関数と最適化手法（optimizer）、学習ループの基本形、CPU／GPU の切り替え（`device`）。強化学習で使う範囲に絞る |

- 概要資料は「仕組みの地図」に留め、細部は演習の各章で実際に動かしながら説明する（概要資料が長くなりすぎて演習に入れなくなるのを避ける）

### 2. Windows での環境構築マニュアル

演習を始めるための環境を、Windows 11 で一から用意する手順書。含める内容（案）:

- Python の導入と、プロジェクト専用の仮想環境（venv）の作成
- PyTorch の導入: CPU 版と GPU（CUDA）版で手順を分けて書く。GPU 版は、NVIDIA ドライバの確認（`nvidia-smi`）と、PyTorch 公式サイトで出せる導入コマンドの選び方を説明する
- Gymnasium（`gymnasium[box2d]`・`gymnasium[mujoco]` 等の追加分を含む）、Stable-Baselines3、`ipykernel` の導入。Box2D は Windows でビルドにつまずきやすいため、必要な追加ツールと、うまくいかないときの対処を書く
- VS Code と Python／Jupyter 拡張機能の準備、Notebook のカーネルの選び方
- 動作確認用の Notebook: 各ライブラリの版の表示、`torch.cuda.is_available()` による GPU の確認、CartPole をランダム方策で1エピソード動かす
- 読者向けの教科書なので、手順は一般的な Windows 環境を想定して書く。コマンドや版の番号は、執筆時に公式ドキュメントで確認したものだけを載せ、確認日も書く

### 3. 演習の章立て

環境の分類と収録環境は公式サイトで確認したもの（2026-10-01 時点）。章の割り振り（どの環境でどの手法を扱うか）は Claude による案で、着手時に見直す。第0章は、概要資料で説明した Gymnasium の API を実際に手で動かして確かめる章とする。

| 部 | 章 | 環境 | 主に扱う手法・概念 |
|---|---|---|---|
| 第0部 | 0 | CartPole 等（ランダム方策） | Gymnasium の API（`reset`／`step`／`observation_space`／`action_space`）、ランダム方策で動かす、エピソード・報酬・終了条件（`terminated`／`truncated`） |
| 第1部 表形式 | 1 | FrozenLake | マルコフ決定過程、価値反復・方策反復（動的計画法）、Q学習 |
| | 2 | CliffWalking | SARSA と Q学習の比較（方策オン／オフの違い、安全な経路と最短経路） |
| | 3 | Taxi | 状態数の多い表形式 Q学習、ε-greedy の探索の減衰、行動マスク |
| | 4 | Blackjack | モンテカルロ法、確率的な環境 |
| 第2部 関数近似 | 5 | CartPole | 状態の離散化の限界 → DQN（経験再生・ターゲットネットワーク） |
| | 6 | CartPole（続き） | 方策勾配法（REINFORCE）、DQN との比較 |
| | 7 | MountainCar／Acrobot | 報酬がまれにしか得られない環境と探索の難しさ、報酬設計（reward shaping） |
| | 8 | Pendulum | 連続行動 → Actor-Critic（DDPG／SAC など） |
| 第3部 物理シミュレーション | 9 | LunarLander | PPO、離散版と連続版の比較 |
| | 10 | BipedalWalker | 高次元の連続制御、学習の安定化、ハイパーパラメータ調整 |
| 第4部（発展・任意） | 11 | MuJoCo（InvertedPendulum → Hopper／Walker2D） | 本格的な連続制御のベンチマーク。計算負荷しだいで扱う範囲を決める |

各章でそろえる項目（案）:

- 環境の説明（状態・行動・報酬・終了条件）を自分の言葉でまとめる
- アルゴリズムの考え方と最小限の数式
- 実装（自作または Stable-Baselines3。章ごとの使い分けは実現方針の分岐点1を参照）と学習の実行
- 学習曲線（エピソードごとの報酬）と、学習後の動きの記録（動画・GIF）
- 前の章の手法がこの環境ではなぜうまくいかないか、という章どうしのつながり

### 4. クラス図（必要になる都度作成）

演習で新しいライブラリの仕組みに触れる時点で、その範囲のざっくりしたクラス図を作る。最初から全体を描かず、必要になった分だけ足していく。

- 目的: 関連ライブラリの主なクラスと、継承・保持の関係をつかむこと。メソッドや属性はすべて書かず、演習で使うものだけに絞る
- 作成の例（どの時点で作るかの案）:
  - 第0章: Gymnasium の `Env`・`Wrapper`・`Space`（`Discrete`／`Box`）の関係
  - 第2部の DQN の自作: PyTorch の `nn.Module`・各層・optimizer・損失関数の関係
  - Stable-Baselines3 を初めて使う章: `BaseAlgorithm` から方策オン型（PPO・A2C）と方策オフ型（DQN・SAC 等）に分かれる継承関係、方策クラス、`VecEnv`、コールバック
- 描き方: **SVG を基本とする**（教科書の図全般の方針。実現方針の「図の形式」を参照）。クラス名と関係は、その時点で使っている版のソースコードか公式の API リファレンスで確かめてから描き、図に対象の版を書く
- 置き場所: SVG ファイルとして保存し、クラス図の説明を書いた Markdown ファイル（`.md`）から画像として表示する。概要資料や各章の Notebook からは、その `.md` にリンクする

## 実現性

技術的な難易度は低〜中。第1部・第2部は Gymnasium と NumPy（DQN 以降は PyTorch）があれば CPU で十分に回せる。難しくなるのは、第3部以降の学習時間と、Box2D／MuJoCo の導入（特に Windows）。教科書としての手間は、実装そのものより、各章の説明文・図・学習曲線をそろえる執筆作業のほうが大きい。

## 実現方針（案）

分岐点1〜3と図の形式は決定済み。残っている未決の点（「着手時に確認」と書いた項目）は着手時に決め、`docs/qa_log.md` に記録する。

- **作る順番**: 概要資料 → Windows での環境構築マニュアル → 演習。クラス図は演習を進めながら必要な分だけ作る
- **MVP**: 概要資料・環境構築マニュアルと、演習の第0部〜第2部（Toy Text と Classic Control）。CPU で回せる範囲で、表形式から DQN・方策勾配までを一通り通す
- **分岐点1: アルゴリズムを自作するか、ライブラリを使うか**
  - 選択肢A: すべて自作する（NumPy／深層学習フレームワーク）。理解は深まるが、第3部以降は実装・デバッグの負担が大きい
  - 選択肢B: [Stable-Baselines3](https://stable-baselines3.readthedocs.io) 等の既存実装を使う。高度な環境まで早く進めるが、中身の理解が浅くなりやすい
  - **決定: Stable-Baselines3 を使う**
  - 使い分け（Claude の解釈。着手時に確認する）: Stable-Baselines3 には表形式の手法（Q学習・SARSA・モンテカルロ法）が無いため、第1部は NumPy で自作する。第2部の DQN・REINFORCE は PyTorch で自作し、同じ環境を Stable-Baselines3 でも解いて結果を比べる。第3部以降は Stable-Baselines3 を主に使う
- **分岐点2: 深層学習フレームワーク**
  - 選択肢A: Keras（Keras 3）。ただし Stable-Baselines3 は内部が PyTorch のため、Keras のモデルを Stable-Baselines3 に渡せず、自作の章と Stable-Baselines3 の章で道具が分かれる
  - 選択肢B: PyTorch。Stable-Baselines3 と同じフレームワークのため、自作したネットワークと Stable-Baselines3 の内部を同じ書き方で読み比べられ、導入するフレームワークも1つで済む。ネイティブの Windows でも GPU を使える
  - **決定: 選択肢B（PyTorch）**。一度は Keras を採用したが、Stable-Baselines3 との組み合わせの問題から取りやめた
- **GPU あり・なしの両対応**
  - Stable-Baselines3 は `device="auto"` で GPU の有無を自動で判定する。自作の章でも `torch.cuda.is_available()` で装置を選ぶ1行だけにし、教材のコードには GPU 専用の処理を書かず、どちらの環境でもそのまま動く形にする
  - 各章の冒頭で、使っている装置（CPU／GPU）を表示するセルを置く。あわせて、CPU だけの場合の目安の学習時間を章ごとに書く
  - 注意: 小さな全結合ネットワーク（`MlpPolicy`）の PPO などは、GPU よりも CPU のほうが速いことがある（Stable-Baselines3 もこの点で警告を出す）。GPU が効くのは、主に画像入力（CNN）や大きなネットワークの場合。第1部〜第3部の大半は CPU で十分で、GPU が効いてくるのは第4部（MuJoCo）以降という見込みを教科書の中でも説明する
  - PyTorch の CPU 版と GPU（CUDA）版は導入方法が違うため、導入手順を両方とも書いておく
- **分岐点3: 教科書の形式**
  - 選択肢A: Jupyter Notebook（説明・コード・グラフを1ファイルにまとめられ、実行しながら読める）
  - 選択肢B: Markdown の本文＋Python スクリプト（Git の差分が読みやすく、他のツールで本の形にしやすい）
  - 条件: ブラウザの GitHub で読めること
  - **決定: 選択肢A（出力を残した Notebook）**。学習曲線や GIF などの結果を、実行しなくても GitHub で読めるため
  - 運用: グラフ・GIF はファイルに保存して参照する。1章を1 Notebook に分ける。コミット前に、出力に個人のパス（`C:\Users\<ユーザー名>\...` 等）が残っていないか確認する
  - **Notebook と Markdown の使い分け（決定）**: Markdown のほうにメリットがある資料は、積極的に Markdown（`.md`）にする。コードを実行する演習は Notebook、コードを実行しない概要資料・環境構築マニュアル・クラス図は Markdown とする。実行しない文章は `.md` のほうが差分が読みやすく、GitHub での表示も安定しているため
  - 開発環境: Notebook でも VS Code で開発できる（Microsoft の Python 拡張機能・Jupyter 拡張機能と、実行環境側の `ipykernel` を使う）。拡張機能とパッケージの導入はユーザー自身が行う
  - Notebook での注意: `render_mode="human"` は別ウィンドウを開くため使わず、`rgb_array` で画像として受け取って GIF に保存する。長い学習は、VS Code を閉じるとカーネルごと止まるため、モデルを途中保存する（Stable-Baselines3 の `save()`／チェックポイント）か、学習部分だけをスクリプトに分けて実行する
- **図の形式**
  - **決定: Mermaid より SVG を優先する**（この教科書についてはユーザーの方針として、グローバルルールの「基本は Mermaid」より優先する）
  - GitHub は、Markdown から相対パスで参照した SVG 画像を表示できる。Notebook の Markdown セルから SVG を参照した場合に GitHub で表示されるかは、着手時に確認する
  - 注意: SVG は座標を1つずつ手で設計するため、Mermaid より作成の手間（トークン）が大きい。作成には `svg-diagram` エージェント（下書き後にレンダリングして、文字の重なりやはみ出しを別の視点で確認する手順を持つ）を使う
  - GitHub は SVG の中のスクリプトを実行しないため、図は静的な内容（文字・線・図形）だけで作る。フォントは読者の環境にあるとは限らないため、一般的なフォント指定にする
- 具体的な執筆・実装は、アイデアを練った元のリポジトリでは行わず、別プロジェクトのフォルダで進める
- **セキュリティ・著作権上の注意（作業PCのセキュリティに配慮する）**:
  - パッケージは PyPI 等の公式配布元からのみ取得し、名前の似た非公式パッケージに注意する
  - 公式チュートリアル・既存書籍のコードや文章は丸写ししない。参考にするときは自分の言葉・自分の実装に書き直し、出典を明記する
  - 教科書を公開する可能性がある場合は、その時点で、参照したコードのライセンスと、第4部や Atari で使うアセット・ROM の利用条件を確認する（公開はしない前提なら、ローカルとプライベートリポジトリでの利用に留める）
- **著者の作業環境での注意**（読者向けの環境構築マニュアルには含めない運用）:
  - パッケージの導入（`gymnasium`、`gymnasium[box2d]`、`gymnasium[mujoco]`、PyTorch、Stable-Baselines3 等）はユーザー自身が行う。導入先（プロジェクト専用 venv など）を先に確認する。Python は `py` ランチャー経由で使う

## 類似の既存事例

- Gymnasium 公式のチュートリアル（上記）が、一部の環境について「この環境をこの手法で解く」形の解説をすでに提供している
- Sutton & Barto『Reinforcement Learning: An Introduction』は、表形式の手法から関数近似へ進む章立ての定番教科書で、第1部・第2部の構成の参考になる
- **差別化点・示唆**: 新しさを狙うものではない。1つの共通の骨組みで環境を順に入れ替え、「前の章の手法がなぜ次の環境で通用しないか」を自分で確かめながら進む、という一本の筋を通すところに、自作する価値がある
